Zstreamer Pipeline Framework

Zstreamer 開發心路歷程

從底層 C/C++ 多媒體 Buffer 設計、OpenGL 視訊合成，到 RTP 網路串流與動態 Pad 解耦。這是一段探索系統極限與架構美學的故事。

Chapter 01

地基構築：核心 Pipeline 與 Element 抽象化

當初決定用 C 語言從零手寫 Zstreamer 時，首要目標就是建立一個極度輕量、低延遲且沒有多餘維護負擔的多媒體 Pipeline。為了做到靈活組合，我參考了標準 Pipeline 哲學，設計了 `Pad`、`Buffer Pool` 以及基礎 `Element` 介面。

「最困難的不是寫語法，而是記憶體生命週期的掌控。多媒體資料流的高頻 Buffer 分配如果每次都重新 malloc，效能立刻拉垮。引進 Refcount 與 Buffer Pool 之後，看到數據傳遞穩如泰山，心中的懸石終於落了地。」
#BufferPool #Refcount #ElementPads #ZeroCopy
Chapter 02

視覺之舞：OpenGL 畫面合成器與 QoS Pacing

有了單路影片播放還不夠，真正的考驗是多路視訊源的混合。我著手打造 `glcompsink`（OpenGL Compositor Sink），支援將多個視訊 Pad 疊加渲染在同一個 3D/2D 紋理看板上。同時導入了 `max_lateness` QoS (Quality of Service) 掉幀機制，防止累計延遲導致畫面卡頓。

「多路影音同步時，如果某一邊的解碼延遲過長，整個繪圖線程會被拖慢。加入 QoS Drop 與 獨立 Worker Thread 上下文初始化後，即便是在高壓串流下，畫面依然能流暢維持 60 FPS 幀率！」
#glcompsink #OpenGL-ES #QoS-FrameDrop #FramePacing
Chapter 03

聽覺重奏：多聲道混音器與 ASRC 漂移補償

影音系統永遠少不了聲音。為了達到完美的音訊混合，我實作了 `audiomixer` Element。它不僅支援多路 request sink pad（`sink_%u`），還具備動態音量調整、獨立 Pan（聲相平衡）以及基於 PTS 的時間戳對齊。面對跨硬體的採樣率漂移，更引入了 ASRC（Asynchronous Sample Rate Converter）漂移補償。

「音訊爆音與相位差是工程師的噩夢。當兩路音訊採樣時脈有微小偏差時，長時間播放一定會發生 Buffer Underflow。寫下 ASRC 漂移補償算法並看到波形順暢銜接時，那種聲音清亮無雜音的感覺真的太治癒了！」
#audiomixer #ASRC-Drift #PTS-Align #PanBalance
Chapter 04

跨越脈動：RTP / SDP 封包與 Pacing 網路傳輸

將本地資料流推向網路世界！在這一階段，Zstreamer 增加了 `net_source`、`net_sink`、`rtp_payloader`（RTP 打包）、`rtpdepay`（RTP 解包）以及 `sdpmuxer` / `sdpdemux`。最為關鍵的是加入了基於時間戳的 Timestamp Pacing，確保 UDP 封包均勻平滑發送，避免突發流量（Burst）造成路由器塞爆 drop 封包。

「網路傳輸坑超級多！直接 sendto 把整個 Video Frame 塞出去會導致 UDP 瞬間爆包落幀。實作了 leaky bucket timestamp pacer 後，看著 Wireshark 裡精準等距的封包時間間隔，整個傳輸品質煥然一新！」
#RTP/RTCP #SDPMuxer #TimestampPacing #UDP-Multicast
Chapter 05

靈魂演進：Adaptive Stream Demuxing 與動態 Pad

在複雜的動態串流情境中，封包格式（Caps）與軌道數量（如 MP4 / MPEG-TS 中的多音軌、多視軌）是在解開串流時才能確知的。我啟動了「Adaptive Stream Demuxing」大重構，重寫 MP4/TS demuxer，讓元素可以在執行期動態建立與連結 Source Pad，並提供安全的多執行緒動態重組。

「動態 Pad 的生命週期管理與鏈結鎖（Thread-safe Pad Linking）是整個架構最優雅也最具挑戰的部分。這代表 Zstreamer 已經從小玩具升華為能夠適應各種複雜多媒體格式的現代化管線框架！」
#DynamicPads #AdaptiveDemux #MPEG-TS #ThreadSafe
