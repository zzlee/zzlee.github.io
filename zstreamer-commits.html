zstreamer / development story

不是再做一個 GStreamer。
而是把「串流」重新拆開。

從 2026-06-09 建庫，到 2026-08-23 已經長成一個 C11、模組化、101+ elements、171+ tests 的 multimedia pipeline framework。這不是單純的 commit timeline，而是一段「需求 → 架構 → 協定 → 硬體 → 測試 → 修正」的工程故事。

Chapter 01 · The seed

先把「串流」變成一個可以組裝的東西

zstreamer 的核心思想很直接：不要讓 source、codec、queue、network、sink 彼此糾纏。讓 element 透過 pad 連接，讓 buffer 帶著資料與 timestamp 穿過 graph，再由 scheduler 決定誰在什麼時候工作。

Chapter 03 · From media to network

當 pipeline 穩定後，世界開始變大

元素逐漸從本地 media processing 延伸到 RTSP、RTMP、SRT、HTTP、HLS、WebRTC 與 RTP；另一條線則往 broadcast infrastructure 前進：ST2110-20/21/22/30/40、PTP 與 ST2022-7 redundancy。

WebRTC

libdatachannel、VP8/VP9、TWCC、ICE、STUN/TURN、SDP。

ST2110

RTP media transport、JPEG XS、PCM audio、PTP timing、redundancy。

HLS / HTTP

內建 HTTP server、live segments、playlist 與 adaptive demux。

Hardware

NVENC/NVDEC、V4L2、VA-API、Intel oneVPL、Jetson、DMABUF/CUDA/Vulkan/oneAPI。

Chapter 04 · The engineering loop

功能越多，測試與文件越不能落後

最近的提交很有代表性：不是只加 feature，而是開始補 encoder/decoder 測試、修正 factory name 與文件 API 範例。這代表專案進入「系統已經夠大，開始治理複雜度」的階段。

Codec tests

h264enc / h265enc / h264dec 補上 property roundtrip、bitstream、pipeline integration、caps verification 等測試。

Documentation correctness

x264_encoder → x264enc、h264_decoder → h264dec、mp4_muxer → mp4mux 等 factory 名稱逐步對齊。

Slice encoding

x264 / x265 加入 slice configuration，開始碰觸低延遲與傳輸友善的 codec tuning。

Epilogue

所以，zstreamer 現在是什麼？

它已經不只是「GStreamer-like C library」。更像是一個把 multimedia pipeline、network transport、clock synchronization、hardware memory 與 runtime plugin 組在同一個可程式化 graph 裡的實驗場。

短期

繼續補齊 codec / protocol 的 test coverage，讓 API 與文件同步演進。

中期

把 hardware allocator、clock/QoS、network congestion 與 zero-copy path 做成可觀測、可 benchmark 的系統。

長期

讓「一條 pipeline」不只是程式碼，而是一個可以視覺化、debug、測量與動態組裝的 runtime graph。
